## Context

The app already has `AuthContext` (with `user.role`), `LocaleContext`
(`locale` + `t`), `AdminRoute`/`AdminOrOwnerRoute`, lazy routes in
`src/routes.jsx`, and two sidebar variants (`Sidebar`, `SidebarV2`). The guide is
read-only, so it needs no API changes and can be fully bundled.

## Goals / Non-Goals

**Goals:**

- Operators can find "what does this term mean?" and "how does this operation
  work?" without leaving the app.
- Sellers see only what they can actually do; admins see the full guide.
- Content is bilingual and searchable.

**Non-Goals:**

- Runtime editing/CMS or a FinteraAPI documentation model. Content is bundled
  and updated with a deploy.
- Replacing the developer docs in `documentation/`.
- Rendering arbitrary user-supplied HTML (raw HTML stays disabled).

## Decisions

### Bundled markdown via Vite `import.meta.glob`

`src/features/docs/content/index.js` loads every `.md` file with
`import.meta.glob("../content/**/*.md", { query: "?raw", import: "default",
eager: true })`. Because the docs page is lazy-loaded, the content lands in the
docs chunk and does not affect first paint. A manifest
(`src/features/docs/data/manifest.js`) maps sections and articles to per-locale
titles, order, and `audience`.

### Role filtering with `audience`

Each article declares `audience: ["admin", "seller"]` or `["admin"]`. The page
reads `user.role` from `AuthContext`, keeps articles whose `audience` includes
the role, and hides sections that become empty. Admin-only articles cover
approvals, project/lot management, and settings/branding. Seller-visible
articles cover viewing, reservations, payments, reports, and terms; the users
article is shared because sellers can view and create users, with admin-only
actions noted inside it.

### Routing and access

Two lazy routes, `/docs` and `/docs/:slug`, wrapped in `AdminOrOwnerRoute`.
That guard already permits admins and sellers; with no `userId` route param it
forbids regular users. The sidebar entry is rendered when
`role === "admin" || role === "seller"` in both `Sidebar` and `SidebarV2`.

### Rendering and table of contents

`MarkdownViewer` renders with `react-markdown` plus `remark-gfm` and
`rehype-slug`. Raw HTML is not enabled. The table of contents queries the
rendered `h2`/`h3` elements from the article container after render, so anchors
always match the ids generated by `rehype-slug` without duplicating the slug
algorithm.

### Search

`fuse.js` indexes the visible articles for the current locale using title and
raw body, memoized on `[locale, role]`. The sidebar filters the article list as
the admin types and shows an empty state when nothing matches.

### Internationalization and styling

Chrome strings (title, search placeholder, empty states, "On this page") live in
`docs.*` keys in `en.json`/`es.json`. Article titles and bodies live in the
manifest and markdown files. Markdown elements are styled through a Tailwind
component map in `MarkdownViewer`, because the typography plugin is not
installed.

## Risks / Trade-offs

- **Content updates need a deploy** → accepted for now; a follow-up change can
  add a FinteraAPI-backed editor.
- **Bundle size grows with articles** → content is isolated in the lazy docs
  chunk; keep articles focused and monitor `npm run build` output.
- **Role filter can drift from API RBAC** → `audience` is declared per article
  and should be reviewed whenever roles/endpoints change.
- **Long articles** → the per-article table of contents mitigates navigation.

## Migration Plan

Additive only: new feature, routes, sidebar items, locale keys, and docs. To roll
back, remove the routes/sidebar entries and the feature directory; no data
migration is involved.
